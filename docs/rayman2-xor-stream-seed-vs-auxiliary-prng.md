# Rayman 2: precise stream XOR state and non-equivalent auxiliary PRNG recurrence

**2026-11-14 — read-only, exact-SHA binary investigation. No decrypted retail EXE.**

## Inputs and provenance

The owner's 676,352-byte CD-sourced PE32 `Rayman2.exe` has SHA-256
`7927a106ac4f2244e304e57c196170f6cfb311af87ddf59eb6e6c48b9bb0d5e3`.
The separately modified 1,468,928-byte GOG PE32 has SHA-256
`9bae484bd84a4afad8d4e7b1bb30a85ce1ce2367f8451463696eabab28a72713`.
GOG is **not** a pristine post-decryption retail executable.

Both inputs contain **byte-identical** `0x44EA23..0x44EA7F` seed
derivation and `0x4510D4..0x451104` reader update sequences.
These are compared only in executable PE sections, with exact binary
instruction anchors, not guessed from a GOG archival `.extra` copy.

## The flag-6 stream seed is not the constructor immediate

At `0x450A2D` constructor `0x450A00` writes `0x6AB5CC79`
to `[stream+0x14]`. This is *not* the effective seed for the
flag-6 read at `0x44EAA0`: retail and GOG both replace it at
`0x44EA7D`. The source is a global DWORD at `0x5116F0`.

1. `0x44EA23..0x44EA2E`: copy the bitwise NOT of byte
   `[0x5116F2]` into byte `[0x5116F3]`. The earlier 3 bytes of
   the global DWORD are left in place.
2. `0x44EA34`: read the modified 32-bit DWORD.
3. `0x44EA3A`: XOR with `0x075BD924`, yielding an unsigned 32-bit
   intermediate `x`.
4. `0x44EA41..0x44EA5A`: multiply `x` by 16807 using shifts,
   LEAs and adds, with native uint32 wrapping.
5. `0x44EA5D..0x44EA6C`: the `0x069C16BD` unsigned `MUL` and
   quotient correction calculate `q = floor(x/127773)` **exactly
   for the full uint32 input domain**.
6. `0x44EA6F..0x44EA7D`: subtract `q * (2^31-1)` from the
   low 32 bits of the multiplication and store the resulting
   uint32 into `[stream+0x14]`.

An exact compact model is:

```python
global_before = read_u32(0x5116F0)  # snapshot BEFORE 0x44EA23
updated = (global_before & 0x00ffffff) | (((~(global_before >> 16)) & 0xff) << 24)
x = (updated ^ 0x075BD924) & 0xffffffff
q = x // 127773
state = (16807*x - q*2147483647) & 0xffffffff
```

Do **not** replace this with unconditional
`(16807*x) % 2147483647`. The x86 code does *not* correct negative
remainders to the usual nonnegative interval. For `x=127773`,
it stores **`0xFFFFF4EC`**, while naive modular arithmetic gives
**`0x7FFFF4EB`**. The exact discrepancy is `0x80000001`
under uint32 arithmetic. The count of all uint32 `x` with a
negative unwrapped remainder is **95,348,946 of 2^32**
(about **2.220016%**). This is a theoretical input-domain count,
**not a measurement of actual runtime game states**.

The reader at `0x451090` XORs each input byte using
`(state >> 8) & 0xff`, then calculates its next state using the
*same* unnormalised uint32 reduction with `x=(state^0x075BD924)`.
Thus the first four mask bytes can be reproduced from a single
runtime snapshot of the original global DWORD; the file's actual
bytes and initial runtime snapshot were **not** available for this
static check.

**Proof of quotient equivalence:** the machine quotient expression is

```python
hi = (x * 0x069C16BD) >> 32
q  = (((x-hi) >> 1) + hi) >> 16
```

The expression is monotone throughout uint32: `hi` and `x-hi`
both cannot decrease as `x` increases by one, because the magic
constant is less than 2^32. Checking **both endpoints of all
33,615 consecutive 127773-wide quotient buckets** (67,230 endpoint
checks) shows `q == x//127773` at every endpoint. Monotonicity then
proves it for every intermediate integer, without brute-forcing
all 4.29 billion inputs.

The independent instruction-by-instruction uint32 simulation and the
compact formula also matched 130,000 consecutive inputs,
100,000 deterministic random full-width inputs and explicit boundary
vectors; these are synthetic tests, not observed game runtime.

## Crucial negative control: the eight pseudo-file generators differ

Two exact owner-supplied auxiliary files have previously been
independently established as **fully regenerated by the *normalised***
masked Park–Miller recurrence:

```
next = (16807 * (current XOR 0x075BD924)) modulo 2147483647
```

Testing their every available adjacent DWORD transition against
**the real stream reader's unnormalised x86 code**, instead of
the normalised arithmetic, produced:

| Exact private sample | Transitions | Normalised model mismatches | Native stream reader mismatches |
| --- | ---: | ---: | ---: |
| `RAYMAN2(1).ICD` (683,565 B; 1-byte prefix) | 170,890 | 0 | **1,957** |
| `dplayerx(4).dll` (165,888 B; no prefix) | 41,471 | 0 | **474** |

The first mismatches occur at zero-based transitions **428** in ICD
and **8** in DPLAYERX. Both input SHA-256 hashes were verified before
comparison. This **distinguishes two related but non-equivalent
state-update implementations**. It is not evidence that the native
reader is invoked on either auxiliary file, or that those samples
contain a decryptable PE payload.

## Correct retail DAT file provenance

The earlier stream flags audit identified an initial
`LEVELS0.DAT` open at `0x44EB40`. This is not necessarily the
actual source of the subsequent flag-6 XOR read.

At `0x44F13A`, retail chooses a **second** DAT filename via
`[EBX*4+0x4A2090]`, opens it at `0x44F17D`, and returns that
second HANDLE at `0x44F1F2`. The following `0x44EA1E`
constructor eventually receives this handle. GOG replaces the
indexed table reference with `[0x4A2090]`, choosing the first
entry, `LEVELS0.DAT`; the retail selector and its bounds depend
on DAT-read runtime data. Neither file path nor selector value
has been witnessed at runtime on a retail CD.
